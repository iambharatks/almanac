# 05 · Data Layer — Postgres, SQLAlchemy, Alembic

> ⭐ **The one idea:** **One engine** (long-lived, pooled, shared) → **many sessions** (short-lived, one per request, unit-of-work). Migrations version the *schema* like git versions the *code*.

---

## 1. Engine vs session ← the core distinction

| | **Engine** | **Session** |
|---|---|---|
| Is | connection manager + **pool** | a **unit of work** (one conversation) |
| Lifetime | **once per application**, shared | **per request**, short-lived |
| Cost | expensive to create | cheap |
| Holds | DB URL, dialect, driver, pooled connections | identity map, change tracking, a borrowed connection |
| Analogy | car **rental company** with a fleet | **one customer's rental** |

**Why pool?** Opening a TCP connection + authenticating costs milliseconds. Doing that per request is wasteful, so the engine keeps ~5–20 connections open and lends them out.

*Java: engine ≈ JDBC `DataSource`/HikariCP pool · session ≈ JPA `EntityManager` (also unit-of-work with change tracking + identity map).*

```python
engine = create_async_engine(settings.database_url, echo=True)   # once
async_session = async_sessionmaker(engine, expire_on_commit=False)  # factory

async def get_db():
    async with async_session() as session:   # borrow
        yield session                         # request uses it
                                              # closed → connection returned to pool
```

`echo=True` prints the generated SQL — invaluable while learning (you literally watch caching work when the SQL *stops* appearing).

## 2. Unit of work — why `add` then `commit`

```python
db.add(url)            # STAGES the change (nothing written yet)
await db.commit()      # flushes everything in ONE transaction (all-or-nothing)
await db.refresh(url)  # reload → now has DB-generated id, created_at
```

The session batches changes and commits atomically. `refresh()` is needed because server-side defaults (`server_default=func.now()`, auto-increment `id`) are only known *after* the DB writes.

## 3. Defining models (SQLAlchemy 2.0 style)

```python
class Url(Base):
    __tablename__ = "urls"

    id: Mapped[int] = mapped_column(primary_key=True)
    short_code: Mapped[str] = mapped_column(String(10), unique=True, index=True)
    original_url: Mapped[str] = mapped_column(String(2048))
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
```

- **Annotation + assignment**, not decorators — `mapped_column` returns a descriptor-backed attribute; the `Mapped[...]` hint is read from `__annotations__`.
- `Base(DeclarativeBase)` — inheriting registers the class as a table; `Base.metadata` is the registry Alembic compares against.
- Class name singular (`Url`), table name plural (`urls`).

**Column flags that carry real meaning:**

| Flag | Effect | Why it mattered |
|---|---|---|
| `primary_key=True` | unique row id, auto-generated | every table needs one |
| `unique=True` | **DB-level** uniqueness guarantee | **caught the short-code collision bug** |
| `index=True` | fast lookups by that column | redirects query by `short_code` on every hit |
| `ForeignKey(...)` | links rows across tables | URL ownership |
| `server_default=func.now()` | the **DB** fills it in | reliable creation timestamps |
| `default="user"` | Python-side default at insert | roles can't be self-assigned at registration |

> 💡 **Indexing is a real design decision.** "Why did you index `short_code`?" → "Every redirect is a lookup by that column; without an index Postgres scans the whole table." That's the interview-grade answer.

## 4. Alembic — migrations

**A migration = version control for your schema.** Each is a numbered, reversible script with `upgrade()` and `downgrade()`.

```bash
uv run alembic init -t async alembic         # async template
uv run alembic revision --autogenerate -m "create urls table"
uv run alembic upgrade head                  # apply
docker compose exec postgres psql -U app -d urlshortener -c "\d urls"   # verify
```

Wiring: `sqlalchemy.url` in `alembic.ini` (which DB) + `target_metadata = Base.metadata` in `env.py` (what the tables *should* be, hence importing your models). Autogenerate **diffs models against the live DB** and writes the delta.

**Two states — the source of most confusion:**
- **Generated** — a file exists in `alembic/versions/`
- **Applied** — it has been run against the DB

⚠️ `Target database is not up to date` = you have a generated-but-unapplied migration. Alembic refuses to stack a new one on top. **Fix: `alembic upgrade head`** — don't regenerate.

⚠️ **Always review autogenerated migrations** before applying. Alembic is good, not perfect.

*Java: Flyway / Liquibase.*

## 5. Adding a NOT NULL column to a populated table

```
column "user_id" of relation "urls" contains null values
```

Existing rows can't satisfy a new NOT NULL rule.

| | Approach |
|---|---|
| **Dev** | delete the rows, re-migrate |
| **Production** | **add nullable → backfill existing rows → alter to NOT NULL** (a second migration) |

> 🎤 That three-step dance is the answer to *"how would you add a required column to a table with millions of live rows?"*

## 6. Querying (async)

```python
result = await db.execute(select(Url).where(Url.short_code == short_code))
url = result.scalar_one_or_none()      # the object, or None
if url is None:
    raise HTTPException(404, "Short code not found")
```

`select(Url).where(...)` is SQLAlchemy's expression form of `SELECT * FROM urls WHERE short_code = ...`. Every `await` here is a yield point — the worker serves other requests while Postgres works.

## 7. Generating unique IDs (the collision lesson)

**Random ≠ unique.** A 6-char random code *can* collide; `unique=True` correctly refused the insert with `UniqueViolationError`.

```python
for _ in range(5):
    candidate = generate_short_code()
    if (await db.execute(select(Url).where(Url.short_code == candidate))).scalar_one_or_none() is None:
        short_code = candidate
        break
else:
    raise HTTPException(500, "Could not generate a unique short code")
```

| Strategy | Trade-off |
|---|---|
| **Random + retry** (used) | simple; retries grow as the table fills |
| Longer code / bigger alphabet | 62⁶ ≈ 56 billion vs 10⁶ = 1M for digits-only |
| **ID → base62** encoding | **collision-free by design**; more complex |

The same generate-check-retry pattern was reused for auto-generated usernames.

## 🎤 Interview answers

**"Engine vs session?"**
> The engine is created once per application and owns a connection pool — it knows how to reach the database and keeps connections open so you're not paying TCP and auth costs per request. A session is a unit of work for a single request: it borrows a pooled connection, tracks the objects you've changed, and flushes them in one transaction on commit. In FastAPI I inject a fresh session per request through a dependency that closes it afterwards.

**"What are migrations and why not just `create_all`?"**
> Migrations are version control for the schema — numbered, reversible scripts that describe each change, so every environment converges on the same structure and you can roll back. `create_all` just builds tables from the current models in one shot; it has no history and no path for evolving a table that already holds data. I use `create_all` in tests for speed and isolation, and Alembic everywhere real.

**"How would you add a required column to a table with millions of rows?"**
> You can't add NOT NULL directly — existing rows would violate it. The safe sequence is three steps: add the column as nullable, backfill the existing rows with a sensible value, then alter it to NOT NULL in a follow-up migration. That way there's no downtime and no data loss.

**"How do you generate unique short codes?"**
> Right now, random 6-character codes from a 62-character alphabet, checked against the database with a retry loop — because random doesn't mean unique, and I hit a real collision that the unique constraint caught. At scale I'd switch to base62-encoding the row's auto-increment ID, which is collision-free by construction and avoids the lookup entirely.

## ✅ Gotcha checklist

- [ ] One engine per app; one session per request
- [ ] `add` stages, `commit` writes, `refresh` reloads DB-generated values
- [ ] "Not up to date" = apply the pending migration, don't generate another
- [ ] Review autogenerated migrations before applying
- [ ] NOT NULL on a populated table → nullable → backfill → enforce
- [ ] Index columns you query by
- [ ] Random ≠ unique — check and retry
- [ ] `echo=True` lets you *see* the SQL (and see caching skip it)
